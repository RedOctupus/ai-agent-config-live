# Patterns

本书中的具体技术、设计模式、算法与工程实践。

## 1. Agent 三元公式
**When to use**: 设计和描述任何 Agent 系统时，作为高层次概念框架。
**How**: 把 Agent 拆成三个组件：LLM（大脑/决策）、上下文（眼睛/观察）、工具（手脚/行动）。
**Trade-offs**: 公式简洁，但每个组件内部都有大量工程细节；不能只换大脑而忽视眼睛和手脚。

## 2. ReAct 循环
**When to use**: 构建需要自主规划、多步执行的 Agent。
**How**: 迭代执行 思考（Thought）→ 行动（Action/Tool Call）→ 观察（Observation/Result）→ 再思考。
**Trade-offs**: 简单通用，但长链容易累积错误；需要错误恢复和回滚机制。

## 3. 工具调用四步流程
**When to use**: 任何需要 LLM 调用外部工具的场景。
**How**: 声明工具 → 模型决定调用 → 执行结果回写上下文 → 模型决定下一步。
**Trade-offs**: 模型自主决策灵活，但要求工具描述清晰、错误处理完善。

## 4. 上下文窗口构成模式
**When to use**: 设计 Agent 的每次 API 调用时。
**How**: 上下文 = system 提示词 + tools 定义 + user 输入 + assistant 历史回复（含工具调用） + tool 结果。
**Trade-offs**: 信息完整但 token 成本高；需要缓存、压缩、分层管理。

## 5. 系统提示词四维设计
**When to use**: 编写或优化 Agent 的系统提示词时。
**How**: 同时设计语气风格（人格）、结构化格式（输出）、组织方式（流程驱动 vs 规则堆砌）、业务规则内容。
**Trade-offs**: 流程驱动适合稳定任务，规则堆砌适合边界复杂任务；混合使用常见。

## 6. 工具五类分类法
**When to use**: 设计 Agent 工具集时。
**How**: 把工具分为感知、执行、协作、用户沟通、事件触发五类。
**Trade-offs**: 分类帮助系统化设计，但具体工具可能跨类；不要强行分类而破坏接口简洁。

## 7. 通用工具优于专用工具
**When to use**: 选择工具粒度或设计新工具时。
**How**: 优先用 Code Interpreter、Bash、Read/Write/Edit、Glob、Grep 等通用工具组合解决问题；只有在参数复杂、安全敏感、性能关键时才做专用工具。
**Trade-offs**: 通用工具灵活、易维护，但模型需要更强的推理能力；专用工具对弱模型更友好。

## 8. Coding Agent 七个核心工具
**When to use**: 构建 Coding Agent 或通用 Agent 时。
**How**: 配备 Code Interpreter、Bash、Read File、Write File、Edit File、Glob、Grep。
**Trade-offs**: 工具极简但组合强大；复杂安全场景需要额外沙箱和权限控制。

## 9. Skill + 通用执行器
**When to use**: 能力变化频繁、模型能力较强时。
**How**: 用自然语言 Skill 描述操作流程，Agent 通过通用工具（如 Bash、Code Interpreter）执行；无需为每个流程创建专用工具。
**Trade-offs**: 灵活、易维护，但对模型理解能力和执行环境要求更高；需要验证输出。

## 10. 上下文压缩与分层
**When to use**: 上下文窗口有限或成本敏感时。
**How**: 区分常驻概览（Advanced JSON Cards）和按需检索细节；用分层压缩、摘要、索引减少一次性加载。
**Trade-offs**: 压缩可能丢失细节；需要保留关键决策点和约束信息。

## 11. 子 Agent 上下文隔离
**When to use**: 多 Agent 系统或复杂任务分解时。
**How**: 每个子 Agent 维护独立上下文，通过显式通信（共享文件、消息总线）交换产物；避免无差别共享完整对话历史。
**Trade-offs**: 模块化和隔离性好，但需要设计清晰的接口和产物格式。

## 12. RAG 管道
**When to use**: 需要把外部知识注入 Agent 上下文时。
**How**: 文档分块 → 嵌入 → 检索 → 重排序 → 生成。
**Trade-offs**: 实现简单但质量取决于分块、嵌入模型、检索策略；复杂知识需要 GraphRAG/RAPTOR 等结构化索引。

## 13. 混合检索
**When to use**: 需要同时兼顾语义匹配和精确关键词匹配时。
**How**: 结合稠密嵌入（语义）和稀疏嵌入（关键词）的结果，经重排序后送入生成。
**Trade-offs**: 比单一检索更稳健，但增加系统复杂度；需要调融合权重。

## 14. 结构化知识索引（RAPTOR / GraphRAG）
**When to use**: 知识复杂、关系丰富、需要多跳推理时。
**How**: 用 RAPTOR 构建递归摘要树，或用 GraphRAG 构建实体关系图。
**Trade-offs**: 比扁平 RAG 表达力更强，但构建和维护成本更高。

## 15. 用户记忆三层次评估
**When to use**: 评估或设计用户记忆系统时。
**How**: 按基础回忆 → 多会话检索 → 复杂联合推理三层递进评估。
**Trade-offs**: 分层评估帮助定位能力短板，但测试数据构建成本高。

## 16. 双层记忆架构
**When to use**: 设计长期记忆系统时。
**How**: 常驻概览（Advanced JSON Cards）提供快速全局上下文 + 上下文感知检索按需取细节。
**Trade-offs**: 兼顾快速访问和精确细节；需要维护两层之间的一致性和索引。

## 17. 三层轨迹验证
**When to use**: 评估 Agent 运行结果或构建持续进化系统时。
**How**: 结果验证器（环境真值）→ 过程验证器（规则/权限）→ 质量验证器（Rubric）。
**Trade-offs**: 越靠下越可靠、越客观；上层依赖 LLM Judge，需要引用证据和拒绝评分机制。

## 18. 评估三层体系
**When to use**: 建立 Agent 评估体系时。
**How**: 评估环境（在哪里测）→ 评估方法（怎么判）→ 评估驱动决策（测了干什么）。
**Trade-offs**: 系统化但建设成本高；初期可从关键任务开始逐步扩展。

## 19. Rubric + 幻觉否决
**When to use**: 对 Agent 输出做自动评分时。
**How**: 把任务拆成多个维度逐项评分；幻觉作为正交否决项，一旦编造事实整体判负。
**Trade-offs**: 比模糊总分更有诊断价值；需要人工定义维度标准和边界。

## 20. 模型替换 + 消融实验
**When to use**: 定位 Agent 性能瓶颈时。
**How**: 模型替换：固定 Harness 换模型，看瓶颈在模型还是 Harness；消融：逐一关闭组件，看各组件贡献。
**Trade-offs**: 实验设计要求高；需要可复现评估环境和足够样本量。

## 21. 三阶段模型训练（预训练 / SFT / RL）
**When to use**: 决定是否需要微调模型或理解模型能力来源时。
**How**: 预训练积累知识 → SFT 学会遵循指令和格式 → RL 学会可迁移决策策略。
**Trade-offs**: 预训练极贵，SFT 便宜稳定，RL 贵但泛化强；多数工程问题先靠 SFT 和上下文工程解决。

## 22. SFT vs RL 决策
**When to use**: 决定用监督微调还是强化学习时。
**How**: 需要稳定格式/流程/风格 → SFT；需要开放环境决策/探索/泛化 → RL。
**Trade-offs**: SFT 易控制但易过拟合；RL 泛化强但训练不稳定、需要仿真环境。

## 23. 持续进化闭环
**When to use**: 构建能从运行经验中学习的 Agent 系统时。
**How**: 执行任务 → 记录轨迹 → 三层验证 → 生成候选更新（知识/指令/程序/参数）→ 回归测试 → 灰度发布 → 进入下一轮。
**Trade-offs**: 闭环能力强但工程复杂；必须防止未经验证反馈被固化。

## 24. 候选更新四层选择
**When to use**: 决定如何修复 Agent 的某类失败时。
**How**: 根据失败诊断指向：知识更新（最快）→ 指令更新 → 程序更新 → 参数更新（最慢、最谨慎）。
**Trade-offs**: 越外层更新越快越安全，但只能修复浅层问题；参数更新最深但风险最大。

## 25. 语音架构三代演进
**When to use**: 设计语音交互 Agent 时。
**How**: 级联（VAD-ASR-LLM-TTS）→ 端到端 Omni（turn-based）→ 全双工（边听边说）。
**Trade-offs**: 级联实现简单但体验差；全双工体验好但延迟和推理控制复杂。

## 26. 快慢思考解耦
**When to use**: 实时交互需要深度思考时。
**How**: 实时交互模型维持低延迟响应，复杂推理委托后台模型或通过 Latent Bridge 异步传递结果。
**Trade-offs**: 提升用户体验但增加系统架构复杂度；需要处理异步结果和上下文一致性。

## 27. 多 Agent 上下文共享 vs 隔离
**When to use**: 设计多 Agent 系统时。
**How**: 信息需要完整继承、角色强相关 → 共享上下文；模块化、独立职责、可扩展 → 隔离上下文 + 显式通信。
**Trade-offs**: 共享上下文易膨胀和泄露隐私；隔离上下文需要设计清晰接口和产物格式。

## 28. Agent 间通信三大机制
**When to use**: 多 Agent 系统需要传递信息时。
**How**: 工具调用参数（同步结构化）、共享文件系统（大产物持久化）、消息总线（异步解耦）。
**Trade-offs**: 工具参数简单直接但同步耦合；文件系统适合大产物但需注意并发；消息总线异步灵活但需编排。

## 29. 基于角色的任务分解
**When to use**: 复杂任务需要多 Agent 协作时。
**How**: 按需求分析师、软件工程师、代码审查员、测试工程师等角色拆分，每个 Agent 专注一种职责。
**Trade-offs**: 分工清晰但接口和产物格式设计是关键；过度拆分会增加协调开销。

## 30. 事件驱动的异步 Agent
**When to use**: Agent 需要响应邮件、Webhook、定时器等外部事件时。
**How**: Agent 注册事件源 → 事件触发 → Agent 唤醒执行 → 完成后进入等待。
**Trade-offs**: 从被动响应变主动，但需要状态管理、错误恢复和重试机制。

## 31. 缓存驱动的上下文设计
**When to use**: 长上下文成本高、延迟敏感时。
**How**: 识别可复用前缀（如系统提示、工具定义、稳定知识），利用 KV Cache 和 Prompt Cache 复用；把易变内容放在可复用前缀之后。
**Trade-offs**: 需要理解 API 和模型缓存机制；收益随对话轮次和上下文规模增加。

## 32. 隐私分级与日志脱敏
**When to use**: 处理用户敏感信息的 Agent 系统时。
**How**: 对记忆、日志、检索结果按敏感度分级；敏感字段脱敏或匿名化；最小权限访问。
**Trade-offs**: 增加工程复杂度；但合规和信任是产品底线。
