### MEMORY 体量（防爆炸）

MEMORY 只保留各阶段**当前一句话**和编码门闸（约束、入口），不是源文件副本。

| 写这里 | 不要写这里，写到 |
| --- | --- |
| 大环境一句话 | 对方怎么办事的正文 → `ENVIRONMENT.md` |
| 需求目的一句话 | 拆开的条目、验收句 → `REQUIREMENTS.md` |
| 框架骨架一句话 | 选型、模块表、分层 → `FRAMEWORK.md` |
| 实现流程一句话 | 步骤、分支、每步 I/O → `FLOW.md` |
| 约束与入口（短） | 函数、参数、schema → 代码；步骤/待办 → `TODO.md`；验证记录 → `tests/`；变更史 → `ITERATION.md` |
| 必知事实（只留指针，见 §0） | 环境 / 路径 / 账号位置 / 工具版本 / 结论 / 坑 → `HANDOVER.md` |
| 外部地址（只留指针，见 §0） | 对标产品文档 / 外部服务端点与本机路径 / 参考仓库 → `REFERENCES.md` |

规则：

- **改写快照，不堆历史。** 源文件改了，只在某阶段一句话变了时改本表；小改动若各阶段一句话和约束都没变，**不要**动 MEMORY。
- **超了就外移。** 单节 >40 行删细节留文件名；全文 >400 行走下方裁剪门闸。
- **§0 只数实义行。** 配额是 **≤ 15 行实义内容 / ≤ 900 字符**，**单行 ≤ 300 字符**。空行、标题、`>` 说明块**不计**——它们不产生阅读负担，却会吃掉行预算（实测 4 个空行占掉 15 行预算的 27%）。
- **指针有两个方向会涨。** ① 竖着长：每加一份 TEST-LOG 链接就多一行 → 旧 TEST-LOG 归档到 `tests/_archive/`，§0 只留**最近一份**，更早的合并成一句「更早见 `tests/`」；**同一主题的多个指针并到一行**。② 横着长：**行数不动、字符在涨**，只数行的门闸一次都不会响 → 由 900 字符预算兜住。
- **每个文件最多链一次。** 同一文件在 §0 链三遍是纯噪音（实测踩过：`HANDOVER` 在「必知事实 / 未决 / 重启」各链一遍）；后续提及用反引号文件名。
- **战报不进 MEMORY。** E2E 逐轮结果 / 逐缺陷状态 / 复跑取证 → `tests/` 各 TEST-LOG，MEMORY（含 §0）只留一句指针。
- **取证不入库。** 截图 / 原始 JSON / stdout / SQL 快照 → `docs/memory/tests/_raw/`，`.gitignore` 加同名路径；只提交手写的 TEST-LOG `.md`。（`tests/` 若按任务分子目录，则用 `docs/memory/tests/*/_raw/`。）

**裁剪门闸（超了就裁，别等它自己瘦）：** 跑 `python scripts/check-memory-size.py`，报超阈值（全文 >400 行 / §0 实义 >15 行或 >900 字符 / 单行 >300 字符）或单节明显 >40 行即触发。
**只外移，不删除：** ① 战报 / 缺陷状态 / E2E 明细 → `tests/`，MEMORY 留指针 ② 模块 / 仓库地图 / 文件索引 → `FRAMEWORK.md` ③ 源文件正文 → 删掉，留文件名 ④ 已过里程碑的正文 → `ITERATION.md` ⑤ 跨阶段必知事实 → `HANDOVER.md` ⑥ 外部对标 / 外部系统地址 → `REFERENCES.md`。裁完再跑一次 check，达标再动手。

**外移必须核对，别靠印象搬。** 外移是「复制 + 删除」两步，凭记忆一次做完最容易漏——尤其是**决策条目**（「XX 未拍板」这类长得像备注，最常被跳过，实测丢过一条）。强制顺序：**先复制到新处 → 逐条回读原处对照（按条目 / 关键词点名核，不靠通读印象）→ 确认零遗漏 → 才允许删原处。**

**目录外的指针**（指向 `docs/memory/` 之外的资产，如 specs / plans / 设计稿）：§0 用**一行**存根收口，同类并到同一行（`见 [specs](…) · [plans](…)`），**不各占一行**。这类指针会随外部工具增长，是 §0 膨胀的第三个来源。

## 6. 协作口令（人用）

```text
【大环境】对齐服务对象大环境：对方现在怎么办事。写入 ENVIRONMENT；MEMORY 只留一句话。
【需求讨论】目的 / 约束 / 验收 / 不做。定稿后写入 REQUIREMENTS 条目，MEMORY 只留一句话目的。
【框架讨论】需求条目已定。框架建立在各技术栈选择上：**每一项**先给候选和取舍，等用户明确同意再写入 FRAMEWORK。禁止自行拍板。能力模块、分层同样先商量。先不定逐步怎么走，更不定代码。
【实现流程】框架已定。端到端数据怎么走、分支与每步 I/O 写入 FLOW，MEMORY 只留链路一句话。
【Plan】文件、步骤、验证；TODO 对应 REQUIREMENTS 的 ID
【对照开发】按 R1、R2… 做，验收勾 REQUIREMENTS 状态
【Agent】按 Plan 最小修改
【验收】给命令和预期输出
【叫停】先别写代码，回到大环境或需求或框架或实现流程
```

大任务：大环境 → 需求讨论（REQUIREMENTS）→ 框架讨论（FRAMEWORK）→ 实现流程（FLOW）→ Plan → Agent。

## 7. 阅读完成门闸（Agent）

编码前必须能回答，否则继续读、禁止编码：

1. 本项目要达成的目的是什么？（第 2 节需求目的；条目打开 REQUIREMENTS）
2. 当前改动属于哪个模块？（第 2 节框架快照；细节打开 FRAMEWORK）数据怎么走？（第 2 节实现流程快照；细节打开 FLOW）
3. 风险与最小修改、怎么验？（第 3–4 节）
4. 不要把源文件正文粘进 MEMORY。
5. 不要为答门闸而把全部 memory 文件读一遍；只打开当前不够的那一份。
6. **大任务**要进 Plan 或写代码时：`FRAMEWORK.md` 仍空 → 先提醒【框架讨论】；`FLOW.md` 仍空 → 先提醒【实现流程】。用户书面确认跳过、或声明这是小任务后，才可以动手。
7. **技术选型硬阀门：** 框架未立或某技术栈用户未点头 → 禁止写入「已定」、禁止按该栈编码。先列出待选，逐项等确认。建议不等于已定。
8. 交付时写测试日志；打钩看 TODO。不要为答门闸去读完全部 `tests/` 或 Skill `references/`。
9. **碰环境 / 路径 / 账号 / 命令前：** 先看 `HANDOVER.md`，并核对它的「核实日期」与顶部「最后核实」没过时。那里的事实**仅供参考**，用前核实；与现场冲突以现场为准。
