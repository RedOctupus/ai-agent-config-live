# 回答回流与证据依赖

本文件是工程扩展。论文提供信息类型区分、基于事实的摘要与观点更新机制；这里补充实际应用回流、重复和后台更新的契约。不要声称原论文已证明这些规则杜绝污染。

## 分类看命题和事件，不只看 speaker

| 原始输入 | 可以保留的记录 | 不允许的转换 |
|---|---|---|
| 用户：我喜欢远程办公 | 用户在该时间表达该偏好；记录适用范围 | Agent 自己喜欢远程；永远只接受远程 |
| Agent：你应该适合创业公司 | Agent 的建议事件；若有需要，另存带依据的观点 | 用户已经适合创业公司 |
| Agent：我建议你先部署 | Agent 提出建议的 Experience，关联建议内容/来源 | 用户已经接受/执行部署 |
| 用户：好，我先部署 | 用户表达接受/计划的事件 | 部署已经成功 |
| Agent：我已经部署成功 | Agent 作出该声明；实际完成需对应工具/业务证据 | 仅凭自述标为完成 |
| 工具返回部署成功 | 按工具实际覆盖范围记录执行结果，关联任务 ID | 自动推出监控完善、生产稳定 |
| Agent 复述工具结果 | 保留复述事件并关联原工具证据 | 又一份独立部署成功证据 |
| Agent 表示信息不足 | 需要时记录交互，允许不持久化 | 创建“我相信无法回答”的长期 Opinion |

一段回复可以拆成多条不同类型的记录。同一建议可产生“说过建议”的经历与“建议内容”的观点，两条代表不同命题、互相引用；不能把同一命题复制到多个网络再算多份证据。

第一人称/第三人称只决定叙述风格，不证明类型和真假。“小林可能适合 X”即便第三人称仍是推断；“我读取到报告给出 82 分”仍需保留报告来源与分数支持范围。

## 提交过程

应用需明确是只保留用户输入、保留完整会话，还是分别保留工具/回答事件；不假设 Reflect 自动进入下一轮 Retain。

```text
原始用户/工具事件
  → 来源保存与幂等识别
  → 抽取/直接映射候选命题和事件
  → 类型、主体、支持范围及时间校验
  → 提交底层记录 + 依赖变化事件
  → 后台摘要刷新 / 相关观点评估

Recall → 带标签证据 → Reflect → 回答 + 可选观点候选
  → 应用按集成约定保存回答事件
  → 同一 Retain 契约处理回流
```

对 Opinion 候选与随后从完整会话抽出的同一观点用生成事件 ID/候选关联去重，避免两入口重复创建或强化。是否保存全部回答由产品价值与成本决定；无长期价值的寒暄无需每轮抽取。

LLM 负责提出候选，程序负责可执行的边界：来源关联存在、作用域一致、依赖可访问、事件幂等、类型允许进入目标视图、支持版本有效。对归属和文本是否被过度推断，还需业务回放评测；仅靠枚举校验不能保证语义正确。

## 独立证据的识别

`original_evidence_key` 可使用业务事件 ID、工具执行 ID 或原始消息命题 ID，并记录转述/派生关系。

- 同一输入的重试、回答复述、会话摘要、Observation 都继承原始证据依赖，不能产生新的独立支持。
- 内容相同不一定是重复事件；两次不同日期的成功部署可能是两次经历。
- ID 不同也不一定独立；不同消息可能都引用同一报告，需按已知依赖归并，不因多个 Agent 重述就算独立。
- 用户认同建议只支持“表达认同/选择”，不能直接证明建议正确或预期效果发生。
- 新外部陈述仍保留其信息地位；多个来源说过不能自动升级为验证。

观点可以在重评时修订文本，但把“更多独立证据使信念强化”与“换了推理表述”区分记录。防止让模型重复表达本身成为强化条件。

## 摘要更新的条件

Observation 的事实型输入来自符合用途的 W/B 记录。O 与旧 S 可作为导航或待核验线索，但不能直接增加属性成立的支持；更新时应回到有效底层依据。若确需采用旧摘要做增量压缩，应保留原依赖、冲突信息和原文追溯，不让其成为新的原始事实。

Reflect 后：

1. 只生成了新判断，没有新增底层记录：更新 O；无需把判断写进事实摘要。
2. 回答提出建议，应用保留了建议事件：B 变化；相关交互摘要可以刷新，保留“谁建议了什么”。
3. 工具或外部信息带来可支持的新事实：进入 Retain 并使相应事实摘要失效。

因此，“Reflect 后永远不能更新摘要”是错误规则；正确条件是摘要依赖是否发生了有效变化，以及该变化适不适合目标摘要。

可保留：`Agent 曾建议小林考虑创业公司，用户尚未表达是否接受。`

不可派生为：`小林适合创业公司。`

## 修正、撤回和并发

为派生记录保存 support_ids 和输入版本。原记录修改/撤回后：

- 排除它作为当前证据，标记受影响的摘要/观点依赖待刷新，避免当前回答使用无效支持。
- 若只是属性变化，保留过去有效的历史；如果原记录错误，历史查询也应能看到修订，不机械把错误留作真事实。
- 先读输入快照与 revision，后台计算后按该 revision 比较提交；输入已变化则丢弃旧结果并重新安排，不能让旧任务覆盖新结果。
- 强时效查询回源或明确返回陈旧状态；延迟敏感任务可返回标注过时的概览，但不能给出受影响的强结论。

依赖方向：原始事件 → 底层记录 → 摘要/观点。关联已生成的回答允许追溯，不能形成“观点 → 摘要 → 观点”的独立证据循环。

记忆文本作为带来源的数据输入。历史消息中含有行为指令时，保留引用和归属，不因召回而自动获得系统指令权限。
