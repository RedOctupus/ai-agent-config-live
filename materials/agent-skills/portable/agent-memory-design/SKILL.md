# Agent Memory Design

把真实的记忆失败转换成最小、可实施、可验证的设计。以 Hindsight 的四类记忆与 retain/recall/reflect 为能力来源，允许采用整套逻辑、选取必要模块，或选择更简单的机制。用用户的语言解释选择理由，难理解处给一个贴合业务的小例子。

## 使用边界与依据

- 用户要求设计时交付设计；要求实现时再修改目标项目。技能调用本身不授权改业务系统、调用付费服务或发布。
- 保留用户指定的框架与现有技术，除非它们与明确要求冲突；指出冲突并给最小调整。
- 这是自包含的工程技能。`hindsight-agent-memory` 可作为额外论文知识源，不是运行依赖；无需默认加载整篇论文。
- 区分 `[论文机制]`、`[工程扩展]`、`[场景假设]`，在容易混淆的设计处标注即可。不要把实验参数、具体模型或本技能的配方宣称为论文必需条件。
- 论文依据：[Hindsight v1](https://arxiv.org/html/2512.12818v1)，重点为 §3–6。若讨论当前 SDK、库能力或部署选项，查项目实际版本与官方来源；未核验的接口明确写为伪代码。

## 先定位业务与失效位置

从对话和相关项目文档提取：期望行为、一个失败轨迹、记忆主体/范围、来源与权威数据、变化规则、现有存储及延迟/成本约束。将关键缺口标为假设或未知，只追问会改变路线或阻止正确实现的问题。已有信息足够时直接给初步方案，不发通用长问卷。

沿真实轨迹诊断：来源是否存在 → 抽取是否保留信息 → 类型/实体/时间是否正确 → 更新是否及时 → recall 是否取回充分证据 → 生成是否正确使用证据。证据已被正确召回而回答仍出错，先修消费契约；不要自动增加数据库或检索通道。

对权威业务状态先确定所有者：订单、工单、余额、任务完成状态等由业务系统决定，记忆保存上下文和历史，不能靠模型回答改变业务事实。

## 选择路线与模块

阅读 [selection-guide.md](references/selection-guide.md)，明确给出路线及决定它的业务证据：

- `simple`：会话状态、业务查询、事件历史或简单检索足够。
- `partial`：选择 Hindsight 的必要能力，接入现有系统。
- `full`：外部事实、Agent 经历、实体摘要与长期可修订判断都参与业务闭环；实现完整逻辑职责，具体通道和部署仍可裁剪。

每个新增模块对应一个失败案例或验收要求，并写出输入、输出、依赖、更新触发、降级、成本与验证。不要用任意打分阈值判定是否采用全套；默认挑选证据支持的最小组合。

需要契约时阅读 [module-contracts.md](references/module-contracts.md)，其中模块为：P 来源与类型、N 叙事抽取、E 实体关联、T 时间版本、S 实体摘要、R 检索预算、G 关系扩展、O 观点修订。模块是职责，可由现有系统提供；不等于独立 Agent、服务、表或数据库。

## 保持信息归属与更新正确

World 记录外部信息及其来源；Experience 记录当前记忆主体的经历/行动；Observation 是事实的中立派生摘要；Opinion 是 Agent 的判断。用户表达的偏好可记录为“用户表达过该偏好”，不要误当 Agent 的观点。记录来源角色和信息地位，避免把 World 名称当成真实性保证。

回答回流、自动摘要或观点更新涉及写库时，阅读 [writeback-and-provenance.md](references/writeback-and-provenance.md)。这些约束适用于相应路径：

- 按命题与言语/行动事件分类，不整段按 speaker 分类。“Agent 建议 X”可以是经历；不能推出“X 成立”。
- 重述与摘要保留原始证据依赖，不产生新的独立支持。建议、计划、接受建议、实际执行、成功结果分别记录。
- 摘要只能从符合目标用途的有效底层记录生成，保留归属与历史范围；修正/撤回触发依赖失效。旧后台任务不得覆盖更新版本。
- Reflect 可形成观点；回答是否回到 Retain 由集成决定。有效新事实或经历进入后才重算相关事实摘要；观点变化本身不升级为事实。
- Recall 和图扩展保留范围、类型、时间、有效性等约束；事实任务不能通过去掉标签混用观点。
- Opinion confidence 是启发式信念强度，不是已校准的正确概率；模型自述、重复回流、派生摘要不能循环强化同一证据。

## 产出可开工的方案

按问题大小调整篇幅；优先展示推荐结果和依据。通常覆盖：

1. 痛点与根因、路线、选中/暂缓能力及理由。
2. 必要数据字段与接口，权威数据归属和现有组件复用方式。
3. 输入 → 写入 → 读取 → 回答 → 回流 → 派生更新的具体轨迹；标清同步/异步及谁拥有写权限。
4. 新增、时间变化、错误纠正、撤回、冲突、重复事件的处理；只展开场景真正涉及的情形。
5. 第一阶段可交付切片、迁移/兼容和回退方法、增加能力的可观察条件。
6. 本业务的输入序列、期望结果、对照与成本指标；不要只说“用 benchmark 验证”。

实现配方按需读 [engineering-recipes.md](references/engineering-recipes.md)。它们是工程示例，不是默认全量基础设施；不要把示例中的数据库、模型、步长或 token 数固定为通用选择。实现前先检查项目现有接口和数据。

## 检查设计是否真的解决问题

阅读 [evaluation-cases.md](references/evaluation-cases.md)，选择本场景相关的回放案例；扩展为用户自己的验收轨迹。比较同一任务、数据和尽可能相同模型/预算的简单基线或现状。记录证据取回率、归属正确性、当前/历史区分、拒答或冲突行为、延迟和成本中相关项。

设计完成前检查：新增组件是否有业务证据；部分能力依赖是否闭合；回流是否将推断洗成事实；摘要能否追溯/失效；预算是否计算实际序列化内容；复杂图与观点机制是否有必要。说明验证属于设计回放、静态检查还是实际运行，不能把未运行的设计称作已验证实现。
