## 改动与影响

| 条款 | 修改 | 实际含义 |
| --- | --- | --- |
| 规则 3 · 精度 | 保留确定性与义务强度；禁止补造原因、机制、频率与事实；保护非自然语言内容 | “可能”不能变成“确定”，“建议”不能变成“必须”；语言润色不顺手修改代码或命令 |
| 规则 4 · 可读性自查 | 新增执行者 / 动作、无依据宣传词、多步指令检查；不强行改写清楚准确的文本 | 写清楚谁做什么，删除空泛评价，将三步及以上操作编号 |
| 冲突裁决 | 明确精度优先于英文词数；步骤不替代实体介绍；用户当轮明确要求优先 | 防止短句规则删掉条件或取消已有格式要求 |
| 英文技术文本（新增） | 主动语态、常见词、完整句、简单时态、20 / 25 词参考、保留必要时态 | 限定到英文技术产物，不把英文语法限制套用中文，不引入全局“只返回改写正文” |
| 语言 | 区分交流语言和产物语言 | 默认中文交流；用户要求英文产物时可以写英文；用户明确指定交流语言时按其要求 |
| 文档元信息 / README | 将账号基线与仓内修订日期、同步状态分开 | 本轮文档修改不会被误读为已更新账号 |

对照 Git HEAD 后，规则 1、2、5 和提交 / PR / 网页验收 / 表述 / 技能共 8 个条款的正文保持一致。规则 2、5 的适用边界在冲突裁决中得到保护。

文本审查（核对条款，不是模型行为实验）：

| 场景 | 核对结果 |
| --- | --- |
| 故障原因只有可能性 | 规则 3 要求保留确定性，不能将可能写成已核实事实 |
| 建议或允许的操作 | 规则 3 禁止升级为必须或要求 |
| 执行者未知 | 规则 4 明确不得编造执行者 |
| 英文条件过长但必要 | 规则 3 与冲突裁决优先，20 / 25 词只是尽量达到的目标 |
