# 兼容层协作方案 — 输出模板

结合用户提供的实际上下文填写；不确定处标注「待确认」。

---

# 1. 需求与现有模块分析

- 当前要实现的目标
- 依赖或可能影响的现有模块
- 是否适合使用兼容层
- 不适合直接修改原模块的原因

# 2. 推荐的兼容层方案

明确说明应采用哪一种方式，并说明理由：

- 包装函数或包装服务
- 接口适配器
- 新旧数据格式转换器
- 插件或扩展点
- 中间层 / 网关层
- 独立的新模块
- 其他合适方式

# 3. 代码边界

| 内容 | 说明 |
| --- | --- |
| 可以新增或修改的目录 / 文件 | 明确到建议位置 |
| 不应直接修改的原模块 | 写明原因 |
| 对原模块的依赖接口 | 写明函数、接口或数据结构 |
| 新增兼容层的对外接口 | 写明调用方式 |
| 兼容层负责人 | 如未提供则标注待确认 |

# 4. 代码归属确认

在提出「直接修改」或「新增兼容层」前，先按以下顺序确认目标代码归属：

1. 优先查看模块负责人表、CODEOWNERS 或协作契约文档
2. 若未登记，用 Git 历史辅助（`git blame`、`git log --follow`、`git log -L`）
3. Git 记录只用于定位沟通对象，不等于模块负责人
4. 无法确认 → 标注「待确认」，不擅自改核心代码

| 目标文件或模块 | 正式负责人 | Git 最近主要修改者 | 归属确认方式 | 是否可直接修改 | 建议动作 |
| --- | --- | --- | --- | --- | --- |

- 如有必要，给出最小可行的代码示例
