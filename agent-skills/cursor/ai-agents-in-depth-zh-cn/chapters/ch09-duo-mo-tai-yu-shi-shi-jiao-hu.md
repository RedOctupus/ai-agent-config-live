# Chapter 9: 多模态与实时交互

## Core Idea
Agent 的交互对象不只是文本和 API。当 Agent 需要听懂语音、操作屏幕、控制机械臂时，进入**多模态实时交互**领域。实时性把问题变难：输入持续流动、输出必须在严格时间预算内给出。核心矛盾是 **“实时响应”与“深度思考”之间的平衡**。

## Frameworks Introduced

- **多模态 vs 实时交互**：静态图像/文档理解已较成熟，可作为感知工具融入通用 Agent；实时语音、Computer Use、机器人控制需要专门架构。
- **语音交互的三种范式**（按 ChatGPT 语音三代演进）：
  1. **级联（Cascaded）**：VAD → ASR → LLM → TTS 串行流水线。延迟高、信息丢失、轮次切换靠静音判断。
  2. **端到端全模态（Omni / Turn-based）**：单一模型直接“听音频、想回复、说出来”。延迟更低，但仍是轮流说话，依赖 VAD 判断轮次。
  3. **全双工（Full-Duplex / Interactive）**：模型边听边说，同时处理输入与输出，每秒多次决策“该说、该听、该停、该打断、还是该调用工具”。彻底取消轮次假设。
- **核心演进主线**：如何摆脱“轮流说话”和 VAD 对轮次的猜测。
- **实时交互与深度思考的解耦**：
  - GPT-Live 模式：实时交互模型把复杂任务委派给后台前沿模型（如 GPT-5.5），自己继续维持对话。
  - Step-Audio R1 模式：把思考“内化”进单一模型，实现“边想边说”。
- **快慢思考并行**：快思考保证实时响应，慢思考在后台做深度推理，通过 Latent Bridge 传递中间结果。
- **流式语音感知替代 VAD + ASR**：用流式音频特征直接输入模型，减少轮次误判和延迟。
- **Computer Use**：让 AI 像人一样操作电脑屏幕，视觉感知 + 动作执行，但成本、延迟、稳定性不如直接代码/API。
- **机器人控制**：毫秒级动作控制，面临“感知-思考-行动”循环的延迟问题，需要快慢思考并行和“走一步看一步”策略。
- **实时动作安全**：基于快思考的行动必须有可挽回机制，避免无法撤销的后果。
- **多模态生成 vs 实时交互**：生图、生视频只是普通工具调用，不属本章实时交互主线。

## Key Concepts

- **VAD（Voice Activity Detection）**：语音活动检测，判断用户是否在说话。
- **ASR（Automatic Speech Recognition）**：自动语音识别，把音频转成文字。
- **TTS（Text-to-Speech）**：文本到语音合成。
- **Omni Model**：端到端全模态模型，能同时处理音频、文本、输出音频。
- **Turn-based Voice**：轮流式语音，模型等用户说完再回复。
- **Full-Duplex Voice**：全双工语音，边说边听、边听边说。
- **GPT-Live / Moshi**：全双工语音交互的代表产品。
- **Latent Bridge**：快慢模型之间传递中间结果的隐式通道，超越纯文本。
- **Streaming Perception**：流式感知，用连续输入特征替代离散轮次检测。
- **Computer Use**：让 Agent 通过视觉和操作控制电脑界面。
- **Robotics Control**：机器人控制，物理世界的实时多模态交互。
- **Latency Budget**：延迟预算，实时交互对响应时间的硬性约束。
- **Real-time Safety**：实时动作的安全性，防止不可挽回的误操作。

## Mental Models

- **Real-time is the new default**：用户期望 Agent 能实时感知和响应，不再满足于“问一句等一句”。
- **Turn-based is a crutch**：轮次假设简化实现，但限制了自然交互；全双工是未来方向。
- **Fast thinking keeps the conversation alive, slow thinking solves the hard problem**：实时交互需要快慢思考解耦。
- **Voice is high-bandwidth interaction**：语音速度约为打字四倍，是重要交互界面。
- **Delegate deep thinking, don't block the user**：复杂推理应在后台进行，不要让用户等待。
- **Physical actions need recoverability**：实时控制中的快思考行动必须有撤销或挽回空间。

## Anti-patterns

- **用级联架构做实时语音**：延迟高、轮次误判、体验生硬。
- **忽视延迟预算**：实时交互对响应时间有硬性要求，不能简单套用文本 Agent 架构。
- **让实时模型做深度推理**：用户等待时间过长，体验差。
- **没有快慢思考解耦**：所有思考都在实时路径上完成，导致要么延迟高要么思考浅。
- **Computer Use 代替代码/API**：成本高、延迟大、稳定性差，应优先用代码或 API 完成。
- **忽视实时动作安全**：基于快思考的行动可能产生不可挽回后果。
- **把多模态生成等同于实时交互**：生图、生视频只是工具调用，不需要实时架构。

## Code Examples

```text
// 语音级联流水线架构
[VAD] --(检测到说话结束)--> [ASR] --(文本)--> [LLM] --(回复文本)--> [TTS] --(音频)--> 用户

// 全双工语音架构
[音频输入] --> [单一模型] --> [音频输出]
              ↓ 同时
        [工具调用决策]
              ↓
        [后台慢思考模型]
```
- **What it demonstrates**：级联架构把任务拆成多个模型，信息传递损失大、延迟累积；全双工架构用单一模型同时处理输入输出，并可将深度推理委托给后台模型。

## Worked Example

**场景：语音 Agent 的“实时天气查询”**

用户说：“北京今天天气怎么样？”

1. **级联方案**：
   - VAD 检测说话结束 → ASR 转文字 → LLM 生成回复 → TTS 播放
   - 延迟：500ms (VAD) + 200ms (ASR) + 500ms (LLM) + 300ms (TTS) = ~1.5s

2. **全双工方案**：
   - 模型流式接收音频，边说边听
   - 听到“天气”后决定调用天气工具
   - 工具返回同时生成口语化回复
   - 延迟可降至 ~300ms
   - 用户可打断：“算了，告诉我上海的”
   - 模型立即切换意图，无需等完整轮次

## Key Takeaways

1. **实时交互是 Agent 跳出对话框的关键一步**：语音、Computer Use、机器人控制都需要多模态实时架构。
2. **语音架构三代演进**：级联 → 端到端全模态 → 全双工。主线是摆脱“轮流说话”假设。
3. **实时响应与深度思考必须解耦**：用快思考维持实时交互，用慢思考/后台模型处理复杂推理。
4. **全双工取消 VAD 轮次假设**：边听边说、边说边听，支持打断和意图切换。
5. **Computer Use 成本高、稳定性差**：能用代码/API 完成时，不要优先用 Computer Use。
6. **物理动作需要可挽回性**：实时控制中的快思考行动必须有安全边界。
7. **多模态生成不是实时交互**：生图、生视频等普通工具调用不在本章主线。
