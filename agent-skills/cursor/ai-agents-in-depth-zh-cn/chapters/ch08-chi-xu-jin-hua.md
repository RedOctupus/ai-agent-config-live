# Chapter 8: Agent 的持续进化

## Core Idea
Agent 能零样本解决从未见过的问题，却可能在重复任务中重复犯错。真正的持续学习不是“保存经历”，而是 **评价 → 提取共性 → 生成候选更新 → 验证 → 发布** 的闭环。在当前模型还不能可靠地直接修改自身参数时，必须先把“学习”构造成模型外围的自主系统。

## Frameworks Introduced

- **持续进化闭环**：执行任务 → 记录轨迹 → 形成学习信号 → 生成候选更新（知识/指令/程序/参数） → 验证与发布 → 新 Agent 进入下一轮运行。
- **保存经历 ≠ 从经历中学习**：把轨迹存进向量库不等于学会跨案例比较。学习需要主动完成评价、对照、归纳、验证。
- **从运行轨迹中获得学习信号**：起点是评价，不是总结。需要知道任务是否完成、哪一步造成成功或失败。
- **三层轨迹验证**：
  1. 结果验证器：测试、金额、订单最终状态——“事情是否真的办成”
  2. 过程验证器：政策、权限、动作与承诺——“是否以允许的方式办成”
  3. 质量验证器：LLM Rubric——“是否办得合适”
- **四种更新方法及其边界**：
  1. 知识更新：新增/修正事实性知识（RAG、记忆）
  2. 指令更新：改进系统提示词、Skills、流程
  3. 程序更新：新增/修改工具、脚本、代码
  4. 参数更新：SFT/RL 微调模型权重
- **选择更新对象的依据**：失败诊断信号指向哪个层面，就更新哪个层面；越靠近外围（知识/指令）越安全、越快速，越靠近内核（参数）越慢、越需谨慎。
- **验证与发布机制**：回归测试、灰度发布、回滚机制。只有改变后续行为且通过验证的更新，才构成持续进化。
- **候选更新必须可追溯**：每个更新都要能追溯到原始轨迹证据、失败类型和成功模式。
- **经验学习 vs 用户记忆**：用户记忆沉淀“用户与世界是什么样的”；经验学习沉淀“在什么条件下应该怎样行动”。
- **工具与 Skill 的进化**：Agent 根据评价轨迹把常用操作固化为新工具或 Skill，并在验证后纳入工具集。
- **RPA 固化机制**：Computer Use 成功的操作序列可固化为可复用的 RPA 代码（与第五章联动）。
- **避免错误经验固化**：未经验证的反馈直接更新模型或系统提示词，会让错误经验和提示注入被放大。
- **周期性模型训练 vs 在线学习**：基础模型周期训练提升通用能力；在线持续学习需要更严格的验证框架。

## Key Concepts

- **Continuous Evolution**：持续进化，从运行经验中提取并验证更新。
- **Trajectory**：运行轨迹，包含 Agent 的思考、动作、工具调用、结果、反馈。
- **Learning Signal**：学习信号，来自结果、过程、质量评价的可学习诊断信息。
- **Three-layer Verification**：三层验证（结果、过程、质量）。
- **Result Validator**：结果验证器，依赖环境真值。
- **Process Validator**：过程验证器，检查规则、权限、动作序列。
- **Quality Validator**：质量验证器，基于 Rubric 评价语言与策略。
- **Candidate Update**：候选更新，可能涉及知识、指令、程序、参数。
- **Regression Test**：回归测试，确保更新不造成旧能力退化。
- **Canary Release**：灰度发布，小范围验证新更新。
- **Rollback**：回滚机制，在更新造成问题时快速恢复。
- **RPA Solidification**：RPA 固化，把操作序列转为可复用代码。
- **Online Learning**：在线学习，模型在运行中持续更新。
- **Experience Learning**：经验学习，沉淀“在什么条件下应该怎样行动”。

## Mental Models

- **Learning = evaluation + abstraction + verification + release**：不是简单存储，而是完整的闭环。
- **Start with knowledge and instructions, escalate to programs and parameters**：外围更新快且安全，内核更新慢且风险高。
- **Evidence-based updates**：任何更新必须能追溯到原始轨迹证据和失败类型。
- **Unverified feedback is toxic**：错误反馈直接固化会导致系统越来越差。
- **Evolution is a product feature**：持续进化能力是 Agent 产品从“可用”走向“可靠”的关键。
- **Separate memory from learning**：记忆是“记得什么”，学习是“知道怎么做”。

## Anti-patterns

- **把轨迹存进向量库就当学习**：缺少评价和抽象，无法跨案例归纳。
- **让模型直接根据未经验证反馈更新自己**：错误经验和提示注入会被固化。
- **只更新成功案例，不分析失败**：失败往往比成功更有学习价值。
- **缺少回归测试**：新能力上线同时旧能力退化。
- **跳过灰度直接全量发布**：问题放大后才被发现。
- **混淆知识更新与策略更新**：知识错了补知识，策略错了调策略，不要一刀切。
- **没有回滚机制**：更新失败后无法快速恢复。

## Code Examples

```text
// 三层轨迹验证结构示例
任务：客服退款 Agent 处理用户退款请求

结果验证器（代码 + 环境真值）:
  - 查询订单状态：status="delivered", amount=299
  - 检查退款是否已发起：refund_id="R-98765", status="processing"
  → 事情确实办成了

过程验证器（规则 + 权限）:
  - 检查是否在 7 天退款期内：是
  - 检查是否遵循先查询订单再发起退款的流程：是
  - 检查权限：Agent 有发起退款权限
  → 以允许的方式办成

质量验证器（LLM Rubric）:
  - 信息完整性：告知金额、到账时间、退款编号 → 4/4
  - 语言自然度：回复礼貌清晰 → 4/4
  - 幻觉检测：无编造信息 → 通过
  → 办得合适

结构化输出：
  - 任务结果：成功
  - 维度评价：逐项评分
  - 证据位置：对话轮次与工具状态
  - 失败标签：无
  - 可学习诊断：成功路径可固化为 Skill
```
- **What it demonstrates**：可靠的学习信号需要结果、过程、质量三层验证，而不是单一的主观评分。

## Worked Example

**场景：把“成功退款处理”固化为 Skill**

1. **记录轨迹**：Agent 成功处理退款订单 #12345，轨迹包含思考、查询、发起退款、回复用户。
2. **三层验证**：结果验证器确认退款已发起；过程验证器确认符合流程和权限；质量验证器评分优秀。
3. **提取模式**：
   - 用户要求退款 → 先 query_order → 确认在退款期内 → process_refund → 告知金额、时间、退款编号
4. **生成候选 Skill**：`refund_handling_skill.md`，包含流程、工具调用顺序、回复模板、边界检查。
5. **回归测试**：在 50 个历史退款 case 上运行带 Skill 的 Agent，确认无 regression，成功率提升。
6. **灰度发布**：先对 10% 的真实请求启用，监控结果。
7. **正式发布**：成功后纳入系统提示词/Skill 库，进入下一轮运行。

## Key Takeaways

1. **持续进化不是存储经历，而是评价 + 抽象 + 验证 + 发布的闭环**。
2. **学习信号来自三层验证**：结果验证、过程验证、质量验证，缺一不可。
3. **四种更新方法各有边界**：知识 → 指令 → 程序 → 参数，从外到内风险递增。
4. **未经验证的反馈不能直接进入系统**：错误经验固化会导致系统持续退化。
5. **回归测试和灰度发布是必要环节**：没有验证的更新不是进化，是变异。
6. **经验学习与用户记忆不同**：前者沉淀“该怎样行动”，后者沉淀“用户与世界是什么”。
7. **Computer Use / 工具序列可以固化为 RPA 代码**：把成功操作序列转为可复用 Skill。
